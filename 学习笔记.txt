========================================================
第一部分  最重要的一条：Streamlit 每次都重跑整个脚本
========================================================

【现象】
在 Streamlit 里，你点一下按钮、输入一句话、上传一个文件，
只要页面有任何交互，Streamlit 就会把整个 .py 文件
从头到尾重新执行一遍。

【记法】
把它想成"每次交互都按了一次 F5"。
不是"页面还在，只是更新了一小块"，是"整篇代码重跑"。

【后果】
1. 普通变量（a = 1 这种）每轮都会被重新赋值，留不住。
2. 想留住的东西，必须放进 st.session_state。
3. 页面上的元素每轮也重新画一遍，所以"画历史"那段代码
   每轮都会跑，只要 state 里有数据，历史就一直在。

【结论】
"没聊天记录"这个问题，90% 是 state 被别人清了，
10% 是根本没存进去。不会是"Streamlit 忘了"。


--------------------------------------------------------
1.1  st.session_state 是什么
--------------------------------------------------------
一个"跨轮次"的小仓库。
只要浏览器不关、不刷新，里面的东西就一直在。

    存：st.session_state.名字 = 值
    取：st.session_state.名字
    安全取：st.session_state.get("名字")

【为什么要用 .get()】
    st.session_state.名字          名字不存在 → 直接报错 KeyError
    st.session_state.get("名字")   名字不存在 → 返回 None，不报错

所以"第一次进来要初始化"这种判断，一律用 .get()：

    if st.session_state.get("current_pdf_name") != uploaded_file.name:
        # 说明是第一次，或者换了新文件 → 初始化

【为什么不写 if "名字" not in st.session_state】
  也能用，但很容易写成下面这种翻车版：

    if "current_name" not in st.session_state or ...:
                       ^^^^^^^^^^^^
    这个键你从来没存过 → 前半句永远是 True → if 永远进
    → 每轮都重置 → 聊天记录每轮被清空

  【教训】键名只要写一次，就要全篇一致。
          存叫 current_pdf_name，查叫 current_name，
          Python 不会提醒你，它只会默默地永远为真。


--------------------------------------------------------
1.2  实战案例：没有聊天记录的那次
--------------------------------------------------------
代码里有一句：

    st.session_state.messages = [{"role":"system", ...}]

这是"整个列表换掉"，不是"加一条"。
只要这行每轮都执行，之前聊的全没了。

同一个道理，判断"要不要重置"的条件写错，
就变成了"每轮都重置"。

【自查方法】
在发请求前把列表打印出来，看终端：

    print(st.session_state.messages)

如果第二个问题时只剩 2 条（system + 这次的问题），
说明列表被清了。这是最快、最直接的定位方式，
不需要猜。


========================================================
第二部分  messages 列表的结构（和 AI 对话的底层）
========================================================
发给 AI 的永远是一个"列表"，每一项也是一本小字典：

    [
      {"role": "system",    "content": "你是……"},
      {"role": "user",      "content": "第一个问题"},
      {"role": "assistant", "content": "第一个回答"},
      {"role": "user",      "content": "第二个问题"},
    ]

三个角色：
    system     设定人设 / 说明书，放在最前面
    user       你说的话
    assistant  AI 说的话

【关键理解】
AI 本身没有记忆。它每次看到的，就是这个列表的全文。
你列表里有几轮，它就知道几轮；列表被清空，它就失忆。

所以"聊天记录"和"AI 的记忆"是同一个东西的两面。

【追加而不是替换】
    st.session_state.messages.append({...})       加一条   ✔
    st.session_state.messages = [{...}]           整个换掉 ✘

【发给前先复制一份】
    messages_to_send = list(st.session_state.messages)

这样临时往里塞文档片段，不会污染真正保存的历史。
示例（检索接入的核心）：

    if st.session_state.get("pdf_chunks"):
        picked = pick_relevant(st.session_state.pdf_chunks, prompt, k=3)
        doc_block = "\n\n".join(picked)
        messages_to_send.append({
            "role": "system",
            "content": "以下是文档中与问题最相关的片段……\n" + doc_block
        })

然后：
    messages=messages_to_send      ← 发这个
    不是 messages=st.session_state.messages

第三部分  RAG 的第一步：分块 + 检索

--------------------------------------------------------
3.1  为什么要分块
--------------------------------------------------------
文档太长，塞不进 prompt（有长度上限，也很贵），
所以先切成小块，提问时只挑最相关的几块送进去。

    split_into_chunks(text, size=300)
    text[i : i+size]     ← 切片，每次取 size 个字

【size 大 / 小 的取舍】
    size 小 → 块数多 → 每块信息少，可能把一句话切两半
    size 大 → 块数少 → 每块信息杂，召回时不够精准

没有标准答案。文件小、问题细 → 小一点（300）；
文件大、问整体 → 大一点（600）。

【range 的步长】
    range(0, len(text), size)
    从 0 开始，每次跳 size，所以 i 会是 0, 300, 600……

--------------------------------------------------------
3.2  字符重叠打分（很粗，但是能跑）
--------------------------------------------------------

    quest_chars = set(question)
    for idx, chunk in enumerate(chunks):
        score = len(quest_chars & set(chunk))

【逐项拆开】
    set(question)          把问题拆成一堆不重复的"字"
    set(chunk)             把这一块也拆成一堆字
    &                      交集，只留"两边都有"的
    len(...)               数一数有几个 → 这就是分数

【enumerate 的作用】
    for idx, chunk in enumerate(chunks):  →  同时拿到序号和内容
    等价于 chunks[i]，但更省事，不会写错下标。

--------------------------------------------------------
3.3  排序：元组是怎么比的
--------------------------------------------------------
    scored.append((score, idx))
    scored.sort(reverse=True)
    top = scored[:k]

存的是 (分数, 序号) 这种元组。
元组比较：先比第一个，第一个相等再比第二个。

【坑】reverse=True 时，并列的会按"序号大的在前"。
结果就是：两块都 6 分，排在前面的是靠后的那块，
和问题语义真正相关的那块反被挤掉。

【这就是字符打分的上限】
它只认"字有没有出现"，不认"意思像不像"。
真正的 RAG 用向量相似度（语义），不是数重叠。

--------------------------------------------------------
3.4  这些报错是什么意思（错误分类）
--------------------------------------------------------
SyntaxError / IndentationError   → 代码写错了（少了冒号、缩进不对）
ModuleNotFoundError              → 环境问题（包没装 / 装错解释器）
NameError                        → 名字打错了或没定义
TypeError                        → 类型不对（对数字用 .append()）
AttributeError                   → 东西没有这个属性（st.sessopm_state）

【两次真实翻车】
1) score.append(...)  →  'int' object has no attribute 'append'
   score 是个数，不是列表；要往列表里加，得用 scored。
2) 函数忘写 return  →  picked 是 None  →  'NoneType' has no len()
   函数里算完了但没交出来，外面拿到的是 None。

【识错口诀】
先看最后一行是什么 Error，再定方向：
  语法类 → 那一行本身
  模块类 → 环境和安装
  其他   → 打印中间变量，看实际值

第四部分  函数与代码组织
========================================================

def 函数名(参数, 参数=默认值):
    """说明"""
    ...
    return 结果

【默认值】
    def split_into_chunks(text, size=300):
    调用时不写 size 就是 300，写了就用你给的。

【有没有 return 的区别】
    有 return → 函数给你一个值，可以 c = 函数()
    没 return → 函数返回 None，你拿到的是"空"

【缩进】
Python 靠缩进判断"谁属于谁"，一律 4 个空格，
不要混 Tab。缩进错了报 IndentationError。

--------------------------------------------------------
4.1  if __name__ == "__main__" 是干嘛的
--------------------------------------------------------
意思是："只有直接运行这个文件，下面的才执行。"

【为什么重要】
Streamlit 跑主文件时，是把它当"直接运行"处理的，
所以写在主文件里的测试代码每轮都会跑一遍。

所以测试代码要放到单独的文件里（比如 chunk_tool.py），
用 `python chunk_tool.py` 单独测，不干扰网页。

--------------------------------------------------------
4.2  pip 装的是什么
--------------------------------------------------------
pip install pypdf     ← 装"包"
pip install python    ← 错！python 是"解释器"，不是包

【一句话】pip 装的是库，解释器是另外装的。
报 ModuleNotFoundError 时，先确认是不是这个环境。

5.2  两个 uploader 抢一个变量名
--------------------------------------------------------
    with st.sidebar:
        uploaded_file = st.file_uploader("上传PDF文档", ...)      # 第 76 行

    uploaded_file = st.file_uploader("上传你的PDF文件…", ...)      # 第 87 行

【教训】

第八部分  2026-11-21 检索实测：为什么它总是选错
========================================================

【怎么测的】
拿《学习笔记.txt》当语料（9461 字 → 16 块，size=600），
写 5 个问题，每题配一个"答案块里一定会出现的词"。
挑 3 块，3 块里只要有一块含这个词，就算命中。

这是个土办法，但它把"准不准"变成了一个数字。

【结果】

    版本                    命中率
    pick_relevant（单字）    3/5 = 60%
    pick_relevant_v2（双字） 2/5 = 40%

16 块里随机挑 3 块，期望命中 3/16 ≈ 19%，
5 题平均蒙中 1.1 题。所以 60% 和 40%
都还在"运气好"的范围内，两者差别是噪声。

--------------------------------------------------------
8.1  发现一：平局规则能毁掉整个排序
--------------------------------------------------------
scored 里存的是 (分数, 序号)，排序写的是：

    scored.sort(reverse=True)

元组比较先比分数，分数相同再比序号 —— reverse=True
时变成"序号从大到小"。等于在 0 分的堆里，
优先挑排在末尾的块。所以分隔线那种全是 "---" 的块
反复被选中。

修法：

    scored.sort(key=lambda t: t[0], reverse=True)

key 只取 [0] 号元素（分数），序号完全不参与比较。
Python 的 sort 是稳定的，同分时保持原来的先后顺序
（也就是序号从小到大）。

修完顺序确实变了，但命中率没变 —— 说明平局不是主因。

--------------------------------------------------------
8.2  发现二：真正的病是"分不出区别"
--------------------------------------------------------
5 个完全不同的问题，选出来的块高度重复：

    "跑，只要 state 里有数据"   ×3
    "------------------"        ×3
    "准答案。文件小"             ×2
    "明是第一次"                 ×2

问什么都选同一批块 = 这个打分根本没有区分能力。

--------------------------------------------------------
8.3  发现三：字面匹配的天花板
--------------------------------------------------------
原因是"的、是、一、了、我、这"这些常用字到处都是。
单字打分被它们垫高；换成双字也逃不掉，
因为"什么""就是""这个"同样每块都有。
分数全挤在 5～8 分，拉不开差距。

所以：单字改双字只是换个姿势，天花板没变。

--------------------------------------------------------
8.4  结论
--------------------------------------------------------
字符重叠这种办法，到这儿就到底了。
再怎么调参数、改排序，都不会质变。

质变要换"意思"而不是"字面"——向量检索。
但那要引入嵌入模型（把文字变成一串数字再比距离），
是下一个阶段的活。

--------------------------------------------------------
8.5  今天最值钱的一句
--------------------------------------------------------
先有尺子，再谈改进。

没有这 5 道题的对照表，你根本不知道改动是好是坏，
只会觉得"好像还行"。有了它，才能说出
"从 3/5 变成 2/5，这个改动没用"。

========================================================
第九部分  2026-11-22 IDF：让常用词变便宜
========================================================

【上一节留下的问题】
昨天发现：五个不同的问题，选出来的块高度重复。
病根不是"字面 vs 意思"，而是"常用词没有权重"——
"的、是、什么"每块都有，把分数全垫平了。

--------------------------------------------------------
9.1  一句话原理
--------------------------------------------------------
    IDF（逆文档频率）：
    一个词在越多块里出现，它越不值钱。

      16 块里 16 块都有 → 权重 ≈ 0
      16 块里 1 块才有  → 权重 ≈ 2.77

--------------------------------------------------------
9.2  代码
--------------------------------------------------------
    def idf_table(chunks):
        df = {}
        for chunk in chunks:          # 一层：遍历每一块
            for g in bigrams(chunk):  # 二层：遍历这一块里的组合
                df[g] = df.get(g, 0) + 1

        n = len(chunks)
        return {g: math.log(n / c) for g, c in df.items()}

    def pick_relevant_v3(chunks, question, k=3):
        weights = idf_table(chunks)
        quest_grams = bigrams(question)

        scored = []
        for idx, chunk in enumerate(chunks):
            shared = quest_grams & bigrams(chunk)
            score = sum(weights.get(g, 0) for g in shared)
            scored.append((score, idx))

        scored.sort(key=lambda t: t[0], reverse=True)
        return [chunks[i] for _, i in scored[:k]]

【和 v2 的唯一区别】
    v2：score = len(共享的组合)          ← 数个数，每个算 1 元
    v3：score = 共享的组合的权重之和      ← 贵的多算，便宜的少算

--------------------------------------------------------
9.3  测试方法的三次进化
--------------------------------------------------------
第一版：数"关键词在不在选中的块里"
   → 分不清"第 1 名命中"和"第 3 名勉强挤进去"

第二版：加排名，看正确答案排第几
   → 这才是检索真正关心的：第一块就够，还是要塞 3 块

第三版：修掉测试数据里的错误
   → 关键词选错题、空字符串、语料含考题

--------------------------------------------------------
9.4  两个把测试搞坏的坑
--------------------------------------------------------
【坑一：空字符串】
    gold = [i for i, c in enumerate(chunks) if "" in c]
    "" in 任何字符串 永远是 True
    → 15 块全被算成"含有关键词" → 判"不唯一" → 整题跳过

【坑二：关键词选太泛】
    "None"、"重跑" 这种词好几块都有。
    无法确定"正确答案是哪一块"，排名就无从谈起。
    规则：关键词必须在语料里只出现一次。

【坑三：语料含考题】
    笔记里的自测题那一段，把 12 道题的原文都抄了一遍。
    无论你问什么，它都能对上 → 命中率虚高到 6/7。
    修法：text = text.split("第七部分")[0]，让自测题不参与检索。

--------------------------------------------------------
9.5  结果（7 道题，15 块，k=3）
--------------------------------------------------------
                第1名  第2名  第3名
    v2（无 IDF）  5      1      1
    v3（有 IDF）  6      1      0

  两版都 7/7 进前三，但 v3 多一个"第 1 名"。
  变化具体落在"set(a) & set(b) 得到的是什么"这题：
  v2 排第 3，v3 排第 1。

【结论】
  IDF 有用，但幅度不大（7 题里只翻转了 1 题）。
  可量化的进步，不是感觉上的进步。

--------------------------------------------------------
9.6  今天的教训
--------------------------------------------------------
1. 没有对照组，就没有"变好"。
   不拿同一把尺子量 v2，v3 的分数再高也只是个孤立数字。

2. 结果反常，先查测试，再查代码。
   空字符串、关键词选错题、语料含考题——
   这三个全是测试的错，但表现出来都像"算法不行"。

3. 改代码，一次只改一处，改完跑一次。
   一口气写 20 行错 5 个，其中 2 个还不报错，
   会白跑好几轮。

--------------------------------------------------------
10.1  向量是什么
--------------------------------------------------------
把一段文字变成一串数字，意思越近，两串数字越像。

    "苹果手机"  → [0.21, -0.05, 0.88, ...]   1024 个数
    "iPhone"   → [0.19, -0.02, 0.85, ...]   1024 个数

这两串很像 → 距离近。而它们的字面一个字都不重合。

判断相关性 = 算两个向量夹角的余弦（0～1，越接近 1 越像）。

不再需要：常用字权重、平局规则、关键词提取。

--------------------------------------------------------
10.2  用本机 Ollama 跑，不装任何东西
--------------------------------------------------------
    ollama pull bge-m3          # 1.2 GB，中文
    POST http://localhost:11434/api/embeddings
    {"model": "bge-m3", "prompt": "要变成向量的文字"}

返回里取 ["embedding"]，就是一个 1024 个数的列表。

【注意】是 http，不是 https。
    https://localhost:11434 → ssl.SSLError: WRONG_VERSION_NUMBER
    用加密的方式去敲一扇普通的门。
    看到 WRONG_VERSION_NUMBER，第一反应查 http/https 写反了。

10.3  实测：分数大概在什么范围
--------------------------------------------------------
    苹果手机 ↔ iPhone        0.80
    苹果手机 ↔ 安卓手机       0.75
    苹果手机 ↔ 香蕉          0.51
    XRD峰拟合 ↔ 任意无关词     0.33 ~ 0.37
    XRD峰拟合 ↔ 曲线拟合      0.69
    XRD峰拟合 ↔ 衍射峰的分解   0.59

【校准线】
    ≈ 0.35  无关
    > 0.45  有点关系
    > 0.65  明显相关
    > 0.75  几乎同一个意思
    只对 bge-m3 成立，换模型要重新量。
更重要的是比大小，不是卡阈值。

10.4  写代码时踩的两个坑
--------------------------------------------------------
【坑一：缩进】
    def pick_relevant_v4(chunks, question, k=3):
        scored = []
        for idx, chunk in enumerate(chunks):
            scored.sort(...)          ← 缩进进了循环
            return [...]              ← 第一轮就 return 空列表

    结果 picked = []，7 道题全部"没进前3"。

    ★ 判据：所有题以同一种方式失败 → 系统性错误，
      不是"效果不好"。先怀疑空变量、循环没进、函数没调用。
      ★ 空列表不会报错，只会让你误以为算法差。

【坑二：关键词多打了字】
    笔记原文："这个键你从来没存过"
    测试写的："因为这个键你从来没存过"   ← 多了"因为"
    → 一个块都找不到 → gold == [] → 被判"不唯一"

    ★ 提示信息要能区分"找到 0 个"和"找到好几个"，
      因为修的方向完全相反。

--------------------------------------------------------
10.6  为什么向量输了
--------------------------------------------------------
1. 题目是"找原句"——关键词在原文里一字不差地出现。
   字面匹配天生占便宜，它不是"解决问题"，是"抄答案"。

2. 只有 15 块，而且是同一本笔记的相邻段落。
   块与块本来就相似，向量分不开。
   向量真正厉害的是"在 500 份完全不同的文档里捞出对的那一份"。

3. 块 600 字太长。一块里有十几个主题，
   向量被平均成"泛泛的技术中文"，指向性变弱。
   真实 RAG 一般喂 200～300 字的块给向量。

--------------------------------------------------------
10.7  最后一击：评价比实现更难
--------------------------------------------------------
那道"我每点一次按钮，之前聊过的东西就不见了"的题：

    v3（IDF）：选中 [2, 1, 0]，正确块排第 1，命中
    v4（向量）：选中 [1, 3, 4]，未命中

    但！v4 选的 1 号块讲的是"每次交互都会重跑整个脚本"，
    对"为什么聊天不见了"这个问题，它其实**更有解释力**。
    2 号块只是恰好含有那句话。

    → "正确答案"是我们用关键词人为定义的，
      不是客观事实。换个定义，胜负就翻过来。

【今天最值钱的一句】
    评价检索比写检索更难。
    你能量出来的东西，取决于你选了什么标准；
    标准选错了，再好的算法也会显示成"不行"。
